# run-progress

Экран чтения (docs/ENGINE.md §6–8, docs/ROADMAP.md, этап 2). Одна функция,
три действия через `body.action`: `get` — какую сцену показать сейчас,
`choose` — записать сделанный выбор, `complete` — закрыть прохождение
якорем и «узнаванием» (1–5).

## Структура

```
index.ts               обработчик Deno.serve: get / choose / complete
deno.json               import map для esm.sh
lib/
  current_scene.ts      какая сцена сейчас — считается из числа отмеченных сцен, курсора в базе нет
  scene_projection.ts    strip осей/веса перед отправкой клиенту (get)
  resolve_choice.ts      choice_id клиента → оси, СОХРАНЁННЫЕ сервером при генерации (choose)
test/                   тесты для всех lib/*.ts на node:test
```

## Почему нет отдельного поля «курсор прохождения»

Текущая сцена всегда выводится из того, сколько различных `scene_id` уже
получили хотя бы одну строку в `choices` (`lib/current_scene.ts`). Это же
правило защищает `choose` от записи не по текущей сцене: если присланный
`scene_id` не совпадает с вычисленной текущей сценой — 409, а не тихая
перезапись прошлого или прыжок вперёд.

Финальная сцена содержит только якорь (`scenes_choices_count` в схеме
разрешает ей 0 развилок), поэтому для неё в `choices` никогда не появляется
строка — `resolveCurrentScene` считает прохождение дошедшим до финала,
когда отмечены все сцены КРОМЕ последней, а не когда отмечена и она тоже.

## Почему клиент не может подделать ось

`choose` принимает только `choice_id` (и, опционально, `decision_ms`,
`avoidance`). Оси, полюс и вес для этого `choice_id` сервер берёт
ИСКЛЮЧИТЕЛЬНО из `scenes.choices` — того, что он сам сохранил при
генерации (`lib/resolve_choice.ts`). Клиент их не присылает и в ответе
`get` не видит (`lib/scene_projection.ts` вырезает `axes`/`weight` из
`choices` и `axis` из `field_task`) — подделать запрос и вписать себе
произвольную ось в профиль выбора нельзя, потому что сервер её не
спрашивает.

Обычный выбор пишется в `choices` как одна строка НА КАЖДУЮ осевую отметку
(развилка может нести 1–2 оси) — это соответствует `choices_shape` в схеме:
непустой выбор обязан иметь `choice_id`+`axis`+`pole`+`weight` разом,
avoidance обязан иметь все четыре `null`.

## Действия

- **get** `{ initData, action:'get', run_id? }` — без `run_id` берётся
  последнее незавершённое прохождение пользователя. Возвращает текущую
  сцену (уже без осей), её `is_final`, и полевое задание сцены, если оно
  есть (тоже без оси).
- **choose** `{ initData, action:'choose', run_id, scene_id, choice_id, decision_ms?, avoidance? }` —
  `avoidance:true` пишет отказ от выбора (без `choice_id`); иначе `choice_id`
  обязателен и должен существовать в `choices` текущей сцены.
- **complete** `{ initData, action:'complete', run_id, recognition_score }` —
  только когда текущая сцена финальная; `recognition_score` — целое 1–5.

## Известные границы этой итерации (не баги, а объявленный объём)

1. **Полевые задания только читаются, не завершаются здесь.** `get`
   возвращает текущее полевое задание сцены как есть; проставление
   `completed_at`/`skipped_at` — отдельная точка входа, которую эта функция
   не реализует.
2. **Гонка при двух одновременных `choose` на одну сцену** не блокируется
   явно (нет уникального индекса на `(run_id, scene_id)` в `choices`,
   допускающего это по конструкции — несколько строк на сцену это норма
   для многоосевого выбора). Повторный `choose` по уже отмеченной сцене
   получит 409 («это не текущая сцена»), потому что счётчик отмеченных
   сцен уже сдвинется — но два параллельных запроса на САМУЮ первую
   попытку теоретически могут оба проскочить проверку до вставки.
3. **`complete` не проверяет, что все обычные (не avoidance) сцены имеют
   ровно один зафиксированный `choice_id`.** Проверяется только что
   прохождение дошло до финальной сцены — детальная проверка целостности
   логов выбора оставлена аналитике профиля выбора (`choice_profiles`).
