# catch-ingest

Единственная точка входа записи в дневник (docs/ENGINE.md §6.1, docs/ROADMAP.md, этап 1).
Принимает POST от миниаппа, проверяет initData Telegram, находит или заводит
пользователя, прогоняет текст через предфильтр безопасности, извлекает
контекст и сущности, пишет `catches` (+ `entities_index`, + `safety_events`
при срабатывании).

Что функция **не делает**: не толкует запись и не генерирует художественный
текст — это отдельный шаг (толкователь), получающий уже сохранённую запись
и обязанный сам пройти полный протокол `safety-guardian` перед генерацией.

## Структура

```
index.ts               обработчик Deno.serve — единственный несамодостаточный
                        для Node файл (Deno.serve, Deno.env, '@supabase/supabase-js')
deno.json               import map для esm.sh
lib/
  telegram.ts           проверка initData (Web Crypto, чистая функция)
  validate.ts           валидация payload до похода в базу
  context.ts            контекст момента: время суток + проброс полей клиента
  entities.ts           извлечение сущностей — heuristic_v0 (см. ниже)
  safety.ts             предфильтр кризисных маркеров и магического мышления
  safety_marker.ts       сопоставление маркеров с enum safety_marker в базе
  cors.ts                CORS-заголовки и обёртка jsonResponse
test/                   тесты для всех lib/*.ts на node:test
tsconfig.json           typecheck lib/ и test/ обычным tsc (не для index.ts)
```

## Почему index.ts не тестируется здесь напрямую

`index.ts` — единственный файл, завязанный на Deno-рантайм (`Deno.serve`,
`Deno.env.get`, бэрный импорт `@supabase/supabase-js`, разрешаемый через
`deno.json`). Вся логика, которую имеет смысл тестировать юнитами, вынесена
в `lib/*.ts` — это чистые функции без побочных эффектов и без Deno-глобалов,
поэтому они работают и в Deno, и в обычном Node (используют только Web
Crypto и стандартный JS). `index.ts` — тонкий склеивающий слой поверх них.

## Переменные окружения (секреты функции)

| Переменная | Зачем |
|---|---|
| `SUPABASE_URL` | для service-role клиента |
| `SUPABASE_SERVICE_ROLE_KEY` | функция сама аутентифицирует пользователя через initData, поэтому работает с сервисной ролью и обходит RLS осознанно — это и есть доверенная граница |

```bash
supabase secrets set TELEGRAM_BOT_TOKEN=...
supabase functions deploy catch-ingest
```

## Известные границы MVP (не баги, а осознанный объём)

1. **Извлечение сущностей — `heuristic_v0`.** Полноценное извлечение образов
   и действий из свободного текста — задача для модели. Подделывать её
   регулярками значит закладывать в аналитику фиктивные данные, а вся защита
   pattern-analytics от апофении стоит на том, что данные настоящие. Поэтому
   `lib/entities.ts` извлекает надёжно только валентность и чувства по
   словарю; `images`/`actions` остаются пустыми до подключения модели. Шов
   для замены — один: сигнатура `extractEntities(rawText)` не изменится.
2. **Get-or-create пользователя не полностью атомарен.** Два первых запроса
   от одного `telegram_id` одновременно теоретически могут создать два
   `auth.users`; проигравший переиспользует строку победителя через уникальный
   индекс на `telegram_id`, но его собственный auth-пользователь остаётся
   сиротой. Смягчается тем, что WebApp обычно шлёт запросы последовательно;
   если станет реальной проблемой — переносить в Postgres-функцию с
   advisory-локом.
3. **Голосовой ввод.** Транскрипция и удаление аудио (CONCEPT 13.1) в эту
   функцию не входят — предполагается отдельный шаг до вызова `catch-ingest`
   (или отдельная функция), который транскрибирует и передаёт сюда уже текст.
4. **Список ресурсов помощи при кризисе — не хардкожен.** Сообщение при
   срабатывании кризисного протокола сознательно не содержит номеров телефонов
   служб поддержки: локализованный, поддерживаемый список — отдельная задача,
   и заведомо неверный номер в safety-критичном пути хуже, чем его отсутствие.
